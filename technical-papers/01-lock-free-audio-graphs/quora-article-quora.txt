How do you implement lock-free synchronization in real-time audio?

When writing digital signal processing (DSP) code in C++, the single most critical invariant is that your execution time must be strictly less than your buffer duration (E_t < L). If your audio callback takes longer to compute than the time it takes the DAC to play the buffer, you get an underrun—which physically manifests as a click or pop in the speakers.

So, how do we guarantee our code never misses its deadline? By treating the audio callback as a mathematically constrained environment where system calls and blocking operations are fundamentally prohibited. 

The Failure of Mutexes

In modern operating systems, the audio thread runs at a "real-time" priority, while the User Interface (UI) thread operates at a lower priority. 

A common anti-pattern in C++ audio development is using a std::mutex to protect a shared parameter (like a volume fader) accessed by both threads. If the UI thread acquires the lock, and the audio thread fires and tries to acquire the same lock, the audio thread blocks. This drops the audio thread's priority down to the UI thread's level (Priority Inversion). If a background task preempts the UI thread, your audio thread is now indefinitely stalled, missing its deadline.

The Solution: Lock-Free Ring Buffers

To safely pass continuous streams of data (like MIDI events or parameter changes), we emulate message passing using a Single-Producer/Single-Consumer (SPSC) lock-free ring buffer.

However, CPU caches can reorder memory instructions. If the producer updates the data array, but the updated write index propagates to the consumer's cache before the data itself, the consumer reads garbage. We enforce memory visibility using C++ atomics:

template <typename T, size_t Size>
class LockFreeQueue {
public:
    bool push(const T& item) {
        auto currentWrite = writeIndex.load(std::memory_order_relaxed);
        auto nextWrite = (currentWrite + 1) % Size;
        
        if (nextWrite == readIndex.load(std::memory_order_acquire))
            return false; // Queue is full

        buffer[currentWrite] = item;
        writeIndex.store(nextWrite, std::memory_order_release);
        return true;
    }

    bool pop(T& item) {
        auto currentRead = readIndex.load(std::memory_order_relaxed);
        
        if (currentRead == writeIndex.load(std::memory_order_acquire))
            return false; // Queue is empty

        item = buffer[currentRead];
        readIndex.store((currentRead + 1) % Size, std::memory_order_release);
        return true;
    }

private:
    std::array<T, Size> buffer;
    std::atomic<size_t> writeIndex{0};
    std::atomic<size_t> readIndex{0};
};

- Producer (push): Updates the write index using std::memory_order_release. This guarantees all prior memory writes (the data) are visible before the index updates.
- Consumer (pop): Reads the write index using std::memory_order_acquire. This guarantees that subsequent memory reads (the data) will see the values written prior to the release operation.

Atomic State Swapping

For heavy data updates—such as loading a new impulse response (IR) or swapping a complex plugin state—ring buffers aren't enough. Furthermore, you cannot allocate memory (new or malloc) inside the audio callback because memory allocation acquires internal OS locks.

The solution is Double-Buffering paired with Atomic State Swapping:

class AudioProcessor {
public:
    void updateStateFromUI(std::unique_ptr<HeavyState> newState) {
        // Exchange the active state with the newly allocated one
        auto* oldState = activeState.exchange(
            newState.release(), 
            std::memory_order_acq_rel
        );
        
        // Push the old state to a garbage collection queue 
        // running on a low-priority thread to safely delete it
        garbageQueue.push(oldState); 
    }

    void processBlock(float* output, int numSamples) {
        // Safely acquire the current state without locking
        HeavyState* state = activeState.load(std::memory_order_acquire);
        
        if (state != nullptr) {
            state->process(output, numSamples);
        }
    }

private:
    std::atomic<HeavyState*> activeState{nullptr};
    LockFreeQueue<HeavyState*, 128> garbageQueue;
};

1. The UI thread allocates memory for the new state and performs heavy computation in the background.
2. The UI thread executes an atomic exchange (std::atomic::exchange) to swap the global state pointer.
3. On the next callback, the audio thread safely reads the new atomic pointer and begins processing instantly.

The old state pointer cannot be deleted immediately, as the audio thread might still be actively processing a block using it. Deletion is deferred using a lock-free garbage collection queue running on a background thread.

This is exactly how the Creation Station Audio Engine is built. By aggressively employing atomic state swapping and SPSC FIFOs, it maintains microsecond-level determinism under heavy loads without dropping a single frame of audio.
