You've built an audio plugin, you mapped a parameter to a UI slider, and everything sounds great until the host DAW sends a massive filter sweep via automation. Suddenly, your audio is crackling with zipper noise, and you realize you have no idea how to safely get hundreds of automation points per second from the UI thread into the real-time audio callback without locking.

The problem with discrete automation

DAWs send automation data as discrete events on the message thread or at the start of an audio block. Audio callbacks run in real-time on a high-priority thread where you absolutely cannot block, allocate memory, or wait on a mutex. 

If you just grab the newest value at the start of your buffer and apply it instantly, you get clicks and zipper noise. Audio needs sample-accurate, smoothly interpolated changes.

Here is the WRONG way to do it:

// THE WRONG WAY
void processBlock(juce::AudioBuffer<float>& buffer, juce::MidiBuffer& midiMessages) {
    // Grabbing the value instantly at the start of the block
    float currentCutoff = filterCutoffParameter->load(); 
    
    // Applying it instantly across the whole buffer
    filter.setCutoff(currentCutoff);
    filter.process(buffer);
}

The lock-free queue

To safely pass automation events from the host or UI into the audio thread, you need a Single-Producer, Single-Consumer (SPSC) lock-free queue. In JUCE, juce::AbstractFifo combined with a pre-allocated ring buffer handles this elegantly.

struct AutomationEvent {
    int sampleOffset;
    float value;
};

class AutomationQueue {
public:
    AutomationQueue() : fifo(1024) {}

    void pushEvent(int sampleOffset, float value) {
        auto writeHandle = fifo.write(1);
        if (writeHandle.blockSize1 > 0) {
            buffer[writeHandle.startIndex1] = { sampleOffset, value };
        }
    }

    bool popEvent(AutomationEvent& event) {
        auto readHandle = fifo.read(1);
        if (readHandle.blockSize1 > 0) {
            event = buffer[readHandle.startIndex1];
            return true;
        }
        return false;
    }

private:
    juce::AbstractFifo fifo;
    std::array<AutomationEvent, 1024> buffer;
};

Interpolation in the audio callback

Once you have the automation data safely in the audio thread, you cannot just jump the parameter value mid-buffer. You must ramp (linear interpolation) from the old value to the new value over time.

JUCE provides juce::SmoothedValue for exactly this purpose.

// THE RIGHT WAY
void processBlock(juce::AudioBuffer<float>& buffer, juce::MidiBuffer& midiMessages) {
    auto numSamples = buffer.getNumSamples();
    
    // Update the target value from your thread-safe mechanism
    smoothedCutoff.setTargetValue(cutoffParameter->load());

    // Process sample by sample to allow the parameter to ramp smoothly
    for (int i = 0; i < numSamples; ++i) {
        float currentCutoff = smoothedCutoff.getNextValue();
        filter.setCutoff(currentCutoff);
        
        // Process a single sample
        for (int channel = 0; channel < buffer.getNumChannels(); ++channel) {
            buffer.getWritePointer(channel)[i] = filter.processSample(buffer.getReadPointer(channel)[i]);
        }
    }
}

Handling sample-accurate events

If a DAW sends multiple automation points within a single audio block (e.g., sample-accurate automation), iterating sample-by-sample and updating targets dynamically is essential. Instead of a single target per block, you drain the lock-free queue and process the buffer in smaller chunks whenever an event occurs.

void processBlock(juce::AudioBuffer<float>& buffer, juce::MidiBuffer& midiMessages) {
    int currentSample = 0;
    int numSamples = buffer.getNumSamples();
    AutomationEvent event;

    while (currentSample < numSamples) {
        int samplesToProcess = numSamples - currentSample;
        
        // Check if there's an event in this block
        if (queue.popEvent(event) && event.sampleOffset < numSamples && event.sampleOffset > currentSample) {
            samplesToProcess = event.sampleOffset - currentSample;
        }

        // Apply new target if we reached an event
        if (currentSample == event.sampleOffset) {
            smoothedCutoff.setTargetValue(event.value);
        }

        // Process the sub-block
        if (samplesToProcess > 0) {
            processAudioChunk(buffer, currentSample, samplesToProcess);
            currentSample += samplesToProcess;
        }
    }
}

APVTS: The high-level wrapper

In the modern JUCE ecosystem, juce::AudioProcessorValueTreeState (APVTS) abstracts a lot of this away. When you call getRawParameterValue() from APVTS, you get an atomic float pointer. The host thread calls setValueNotifyingHost() which updates this atomic variable.

However, APVTS alone doesn't handle the smoothing. It gives you lock-free thread safety via std::atomic, but it's still on you to feed those atomic values into a juce::SmoothedValue or juce::LinearSmoothedValue inside processBlock to prevent the zipper noise. APVTS gets the value across the thread boundary safely; parameter smoothing makes it sound good.

Summary

- Never use mutexes, locks, or allocations in the audio callback.
- Pass data across boundaries using std::atomic (for single current values) or a lock-free queue like juce::AbstractFifo (for sample-accurate event streams).
- Never apply large parameter changes instantly. Always ramp values using juce::SmoothedValue to avoid clicks and zipper noise.
- Process your audio buffer in sub-blocks if you need sample-accurate precision for multiple automation events.
