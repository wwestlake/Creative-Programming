Your audio callback fires every 5-10ms whether you're ready or not. If your processing thread isn't keeping up — or if you're writing to a buffer at the same time the callback is reading from it — you're going to get glitches, crashes, or both. A ring buffer solves this without a mutex, which would be fatal in a real-time context.


Why audio specifically needs a ring buffer

Audio runs on two timelines that don't cooperate:

- The audio callback runs on a real-time thread managed by the OS audio driver. It is given a hard deadline. It cannot wait.
- Your processing code (DSP, UI metering, network sends, file writes) runs at its own pace, on a normal thread.

These two sides need to exchange data continuously. The naive solution — a shared array protected by a std::mutex — is catastrophic: if your processing thread holds the lock when the audio callback fires, the callback blocks, the driver misses its deadline, and you get a dropout.

The ring buffer (circular buffer / FIFO) solves this because writes and reads never touch the same memory at the same time, as long as you follow one rule.


The key property: Single Producer, Single Consumer

If you have exactly one writer and exactly one reader, you can implement a lock-free ring buffer using just std::atomic indices. No mutex. No spinlock.

- The producer owns head — it writes and then advances head.
- The consumer owns tail — it reads and then advances tail.
- Neither side modifies the other's index.

This is called an SPSC (Single Producer, Single Consumer) queue. It is the only case where the lock-free ring buffer is correct without additional synchronization primitives.


A clean, correct implementation from scratch

[CODE BLOCK]
#include <atomic>
#include <array>
#include <optional>
#include <cstring>

// Power-of-two capacity for cheap modulo via bitmasking
template <typename T, size_t Capacity>
class SPSCRingBuffer
{
    static_assert((Capacity & (Capacity - 1)) == 0,
                  "Capacity must be a power of two");

public:
    SPSCRingBuffer() : head_(0), tail_(0) {}

    // Called from the PRODUCER thread only (e.g. audio input callback)
    // Returns false if the buffer is full
    bool write(const T* data, size_t count)
    {
        const size_t head    = head_.load(std::memory_order_relaxed);
        const size_t tail    = tail_.load(std::memory_order_acquire);
        const size_t avail   = Capacity - (head - tail);

        if (count > avail)
            return false;

        for (size_t i = 0; i < count; ++i)
            buffer_[(head + i) & mask_] = data[i];

        head_.store(head + count, std::memory_order_release);
        return true;
    }

    // Called from the CONSUMER thread only (e.g. processing thread / UI)
    // Returns number of items actually read
    size_t read(T* dest, size_t count)
    {
        const size_t tail    = tail_.load(std::memory_order_relaxed);
        const size_t head    = head_.load(std::memory_order_acquire);
        const size_t avail   = head - tail;

        count = std::min(count, avail);

        for (size_t i = 0; i < count; ++i)
            dest[i] = buffer_[(tail + i) & mask_];

        tail_.store(tail + count, std::memory_order_release);
        return count;
    }

    size_t availableForRead() const
    {
        const size_t head = head_.load(std::memory_order_acquire);
        const size_t tail = tail_.load(std::memory_order_relaxed);
        return head - tail;
    }

    size_t availableForWrite() const
    {
        const size_t head = head_.load(std::memory_order_relaxed);
        const size_t tail = tail_.load(std::memory_order_acquire);
        return Capacity - (head - tail);
    }

private:
    static constexpr size_t mask_ = Capacity - 1;

    // Pad to separate cache lines -- prevents false sharing between threads
    alignas(64) std::atomic<size_t> head_;
    alignas(64) std::atomic<size_t> tail_;

    std::array<T, Capacity> buffer_;
};
[END CODE BLOCK]

Memory order breakdown:

- Producer loads tail with acquire — sees consumer's latest committed read
- Producer stores head with release — makes new data visible to consumer
- Consumer loads head with acquire — sees producer's latest committed write
- Consumer stores tail with release — makes consumed space visible to producer
- Each thread loads its own index with relaxed — only that thread modifies it, no sync needed

The relaxed load of the thread's own index is safe because only that thread ever writes it — there's no race to observe.


The cache-line alignment trick

[CODE BLOCK]
alignas(64) std::atomic<size_t> head_;
alignas(64) std::atomic<size_t> tail_;
[END CODE BLOCK]

Without this, head_ and tail_ could share the same 64-byte cache line. When the producer updates head_, the CPU has to invalidate that cache line on the consumer's core — even though the consumer only cares about tail_. This is called false sharing and it silently kills throughput. alignas(64) forces them onto separate lines.


Usage example

[CODE BLOCK]
// 4096-sample buffer of floats -- declare globally or as a member
SPSCRingBuffer<float, 4096> audioFifo;

// Audio INPUT callback (producer) -- called by the driver
void MyAudioProcessor::audioDeviceIOCallback(const float** inputChannelData,
                                             int numInputChannels,
                                             float** outputChannelData,
                                             int numOutputChannels,
                                             int numSamples)
{
    // Push captured audio into the ring buffer
    // If full, we drop -- acceptable for a metering use case
    audioFifo.write(inputChannelData[0], (size_t)numSamples);
}

// Processing thread (consumer) -- e.g. an FFT analyser
void AnalyserThread::run()
{
    float chunk[512];
    while (!threadShouldExit())
    {
        size_t got = audioFifo.read(chunk, 512);
        if (got > 0)
            processFFT(chunk, got);
        else
            wait(1); // no data yet, yield
    }
}
[END CODE BLOCK]


Production alternative: JUCE AbstractFifo

Rolling your own ring buffer is educational, but JUCE ships AbstractFifo — a battle-tested SPSC index manager that handles the tricky wrap-around arithmetic for you. You supply the backing array; it manages head and tail.

[CODE BLOCK]
#include <juce_core/juce_core.h>

class AudioFifo
{
public:
    AudioFifo(int capacity)
        : fifo_(capacity), buffer_(1, capacity)
    {}

    // Call from audio callback (producer)
    void push(const float* data, int numSamples)
    {
        int start1, size1, start2, size2;
        fifo_.prepareToWrite(numSamples, start1, size1, start2, size2);

        if (size1 > 0)
            buffer_.copyFrom(0, start1, data, size1);
        if (size2 > 0)
            buffer_.copyFrom(0, start2, data + size1, size2);

        fifo_.finishedWrite(size1 + size2);
    }

    // Call from processing thread (consumer)
    int pull(float* dest, int numSamples)
    {
        int start1, size1, start2, size2;
        fifo_.prepareToRead(numSamples, start1, size1, start2, size2);

        if (size1 > 0)
            memcpy(dest, buffer_.getReadPointer(0, start1), size1 * sizeof(float));
        if (size2 > 0)
            memcpy(dest + size1, buffer_.getReadPointer(0, start2), size2 * sizeof(float));

        fifo_.finishedRead(size1 + size2);
        return size1 + size2;
    }

    int available() const { return fifo_.getNumReady(); }

private:
    juce::AbstractFifo fifo_;
    juce::AudioBuffer<float> buffer_;
};
[END CODE BLOCK]

AbstractFifo::prepareToWrite / prepareToRead return up to two regions because the write may wrap around the end of the buffer. You handle both. finishedWrite / finishedRead atomically commit the index update. The same SPSC guarantee applies — one thread writes, one thread reads.


The common mistake: SPSC becomes MPMC

If you add a second producer or a second consumer, the lock-free guarantee breaks.

WRONG — two producers, no lock:

[CODE BLOCK]
// Thread A (audio callback):
audioFifo.write(inputData, 256);   // <- races with Thread B

// Thread B (network receive thread):
audioFifo.write(networkData, 128); // <- both advance head_ concurrently
[END CODE BLOCK]

Two threads both load head_ with relaxed, both compute available space against the same stale tail_, and both store an overlapping head_ value. Data is corrupted. There is no atomic operation that makes two separate writers safe without a lock.

RIGHT — guard with a mutex at the writer side only:

[CODE BLOCK]
std::mutex writeMutex;

void safeWrite(const float* data, size_t n)
{
    std::lock_guard<std::mutex> lock(writeMutex);
    audioFifo.write(data, n);
}
[END CODE BLOCK]

Since only the writers need the lock (the reader remains lock-free), this is acceptable if the writers are not on the real-time thread. If a producer is on the real-time thread, redesign so that thread is the sole writer.


When to roll your own vs. use AbstractFifo

- Learning how SPSC works → Roll your own (~50 lines, great exercise)
- JUCE project, audio-to-analysis pipeline → AbstractFifo + AudioBuffer
- JUCE project, sending arbitrary structs → AbstractFifo over a std::array<MyStruct>
- Non-JUCE project, production use → folly::ProducerConsumerQueue or boost::lockfree::spsc_queue
- Multiple producers or consumers → Use a mutex or a true MPMC queue


Summary

- A ring buffer lets the audio callback and your processing thread exchange data without blocking either side.
- The lock-free guarantee holds only for Single Producer, Single Consumer. Add a second writer or reader and you need a lock.
- Use std::memory_order_acquire / release for cross-thread index reads/writes. Use relaxed only when loading your own index.
- Align head_ and tail_ to separate cache lines to avoid false sharing.
- In a JUCE project, prefer AbstractFifo — it handles wrap-around and is already correct.
- If a real-time thread is a producer, it must be the sole producer. Never lock on the audio thread.
